# 架构设计 · Cleaner-C（C 盘 AI 分析清理工具）

> 文档定位：**技术架构**。产品需求见 [PRD.md](PRD.md)，排期见 [ROADMAP.md](ROADMAP.md)。
> 本文件中的所有性能与占用数字**均来自本机真实探测**，见文末[附录 A](#附录-a本机实测基线)。

---

## 1. 技术选型（已定，2026-09-17 修订）

**纯 .NET 宿主 + 浏览器 UI**：后端整体为 **ASP.NET Core（.NET 10）** —— MFT 扫描内核、规则引擎、AI 网关、SQLite 索引、HTTP/SSE 服务全部在**同一进程**内；前端仍为 Vite + React + TS，构建产物由宿主直接托管。

> **为什么从 Node 改为 .NET（决策依据）**：本次确定以 **MFT 加速**为核心路线，而 MFT **必须原生代码 + 管理员权限**（实测非管理员 `CreateFile('\\.\C:')` 返回 `Win32Error=5`）。本机无 Rust 工具链，Node 也无标准库支持直读卷。若保留 Node 宿主，就必须叠加 .NET sidecar —— **两个运行时 + IPC + 打包翻倍**；改为纯 .NET 宿主后是**单一进程、单一运行时、单一产物**，且本机已装 .NET SDK 10.0.302，无需新增工具链。
>
> 骨架代码尚未编写，因此**本次改向无返工成本**。

| 决策 | 选择 | 理由 |
|---|---|---|
| 宿主运行时 | **.NET 10（ASP.NET Core）** | MFT 原生实现与 Web 服务同进程；本机 SDK 10.0.302 已装，零额外工具链 |
| 扫描内核 | **C# 直读 NTFS `$MFT`** | **实测 2.19 s** 处理 989,696 条记录（Node 目录遍历 87.8 s，约 **40 倍**） |
| 用户界面 | Vite + React + TypeScript，浏览器访问 `127.0.0.1:<port>` | Treemap 生态成熟（d3-hierarchy）；调试成本最低 |
| 服务形态 | 本地 HTTP 服务，仅监听回环地址 | 天然支持「边扫边看」（SSE 流式推送），也为后续换壳留好边界 |
| 索引存储 | **Microsoft.Data.Sqlite** | 官方驱动，避免第三方原生依赖风险 |
| 权限 | **强制管理员**（清单 `requireAdministrator`） | MFT 直读的硬性前提；已实测非管理员必然失败 |
| 分发 | **自包含单文件**（`PublishSingleFile` + 压缩） | 用户零运行时安装；实测控制台基线 **37.58 MB**（见 §10） |

> **已作废方案**：早期规划的"Node 后端 + `worker_threads` + `node:sqlite` + Node SEA 打包"**全部作废**。相关实测数据保留在附录 A（作为历史记录与对照基线），**不再作为实现依据**。

**关键边界**：规则引擎是**纯函数**（输入节点特征 → 输出分类/风险/文案），不依赖网络。AI 网关是**可选增强层**，可整层关闭而不影响其余部分。这条边界保证"无 Key 时功能完整"不是口号。

**回退路径**：仅当目标卷**不是 NTFS**（ReFS / exFAT / FAT32）或 MFT 读取失败时，才切换到目录遍历实现（`IDirectoryScanner` 的第二个实现）。这是**正确性兜底**，不是性能路径。

## 3. 扫描引擎（MFT 直读）

### 3.1 路线确定：MFT 直读

| 路线 | 本机实测 | 结论 |
|---|---|---|
| **NTFS `$MFT` 直读** | **2.19 s 处理 989,696 条记录**（纯解析 1.80 s）；`$MFT` 966.5 MB、6 个数据运行、记录 1024 B、簇 4096 B；**解析错误 0** | ✅ **已采用（M1 主引擎）**；需管理员 |
| Node 有界并发目录遍历 | 87.8 s（757,385 文件 / 191,877 目录） | ❌ 已弃用（约慢 40 倍） |
| Node 同步单线程遍历 | 153.4 s | ❌ 已弃用 |
| `robocopy /L /E` | 仅测 `System32` 4.0–7.4 s | ❌ 放弃（输出解析脆弱、无硬链接信息） |
| 目录遍历（.NET 实现） | 未单独实测 | 仅作**非 NTFS 卷回退** |

**为什么快**：目录遍历要对 75 万+ 个对象各做一次系统调用；MFT 直读只顺序读取一个 966 MB 的文件，其余全在内存解析。**实测约 40 倍加速**，瓶颈从"元数据系统调用"变为"顺序读 + CPU 解析"。

> 完整原始报告与源码见附录 A.9。

### 3.2 MFT 实现的工程要求

1. **必须提权**：实测非管理员打开 `\\.\C:` 返回 `Win32Error=5 (ERROR_ACCESS_DENIED)`。应用清单设 `requireAdministrator`，启动即提权（产品决策见 [PRD.md](PRD.md)）。
2. **扇区对齐**：卷句柄要求读取的**偏移与长度均按扇区（512 B）对齐**，否则 `ReadFile` 返回 `err=87`。实现中统一向下取整偏移、向上取整长度。（本 spike 已踩此坑。）
3. **引导扇区两个字段是"有符号单字节"**：`0x40`（每记录簇数）与 `0x44`（每索引簇数）。实测本机 `0x40 = 0xF6`，即 `-10` → 记录大小 `1 << 10 = 1024`。**若读成 4 字节整数会得到 246 的错误值**，导致后续读取非对齐而全线失败。（本 spike 已踩此坑。）
4. **必须应用 USA（更新序列数组）修复**：每条记录读取后，按 `0x04`/`0x06` 字段修复各扇区尾部的 USA 占位值。
5. **顺序流式解析**：按数据运行（run list）分块读取（本机 6 个运行），块大小 16 MB 逐块解析，避免一次性载入 966 MB。
6. **重解析点不跟随**：实测 **41,990** 个重解析点记录；junction / symlink 只记录、不递归（防循环与双重计数）。
7. **协作式取消**：支持中断，取消后已解析部分仍可用于展示。

### 3.3 正确性陷阱（硬性要求）

> 统计错了，后面的 AI 解释再漂亮也是误导。以下四条均为本次实测得出的**硬性要求**。

#### (1) 硬链接去重 —— 必须去重，键必须为 64 位

以 **记录号（FRN）** 为键去重：每个在用 FILE 记录即一个物理文件，天然唯一。

**实测证据**：MFT 报 **724,225 个物理文件**，Node 目录遍历报 **757,385 个** —— 多出的 33,160 正是硬链接重复计数。实测有 **25,182 个文件拥有多个真实名字项（硬链接）**。

**两种口径都要算，且都要能展示**：

- `logicalSize`（各硬链接相加）—— 回答"这个目录看起来多大"；
- `physicalSize`（去重后）—— 回答"删掉它到底能释放多少"，**AI 的"预计可回收"必须以此为准**。

> **一处风险消除**：早期文档要求"Node 下必须用 BigInt 读 `ino`"（实测 ino 达 2.36e16，超过 `Number.MAX_SAFE_INTEGER`）。**C# 的 `long`/`ulong` 天然 64 位，该隐患不复存在** —— 这是改用 .NET 附带消除的风险点。

#### (2) DOS 8.3 短名别名 —— 必须按命名空间过滤（新增，实测发现）

`$FILE_NAME` 属性可能有多条，其中**命名空间 `2` 是纯 8.3 短名别名**，并非独立的用户可见条目。

**实测证据（本机全盘）**：

| 口径 | 数值 |
|---|---|
| 物理（每记录一次） | **117.92 GB** |
| 逻辑（仅真实名字项，ns≠2） | **122.60 GB**（差额 4.68 GB = 真硬链接） |
| 逻辑（含 DOS 别名） | **185.26 GB（虚高 51%）** |

名字项共 **1,647,126** 个，其中 **642,368 个是 DOS 别名（占 39%）**。

**要求**：计算逻辑口径时必须**只计入 ns≠2 的名字项**，跨目录聚合同理。忽略此点会虚报 **51%**，比硬链接口径的 3.8% 严重一个数量级。

#### (3) 孤儿记录 —— 父指针为 0 时不可直接丢弃（新增，实测发现）

**实测**：**11,455 条记录**的父目录 FRN 为 0。其中一条 WinSxS 组件目录（`amd64_microsoft-windows-...el-gr_...`）自身父指针为 0，导致其下 **285,877 个文件**无法归属，**45.59 GB 落入"未归属"**。

**要求**：

- 不能只依赖 `$FILE_NAME` 的父指针。父指针为 0 时按序回退：① 该记录其它 `$FILE_NAME` 项的父指针；② 通过目录索引（`$INDEX_ALLOCATION` / `$I30`）反向建立父子关系；③ 对该子树补做一次目录遍历。
- **"未归属"必须作为显式分类呈现**，给出体量与原因，**不得静默丢弃**（与权限披露同一条原则）。

#### (4) 权限与完整度 —— 结论已改变

**实测**：非管理员目录遍历读不到 219 个目录（含回收站 2.28 GB）；而 **MFT 直读绕过 ACL**，这些对象在 MFT 中**名字与大小均可获得**。

**要求**：

- **分析层面**：MFT 使"未授权目录"问题基本消失，**扫描结果不再是"下界"** —— 这是采用 MFT 的重要收益，UI 应从"常驻告警"改为正常状态。
- **操作层面**：**能否删除**仍受 ACL 限制。因此"可清理"的判定必须区分**"看得见"与"删得掉"**，对权限不足项明确提示，而不是让删除操作失败。
- 仅当回退到目录遍历（非 NTFS 卷）时，才恢复"未授权目录披露"逻辑。


#### (5) 回收站 —— MFT 可见，但仍需补全语义

**实测变化**：非管理员目录遍历**完全看不见**回收站（`C:\$Recycle.Bin\S-1-5-18` 为 EPERM，实测 2.28 GB / 2,140 项）；而 **MFT 直读能看到 `$Recycle.Bin` 下的 `$R*` 记录**（名字与大小），**"看不见"的问题已解决**。

**要求**：`$Recycle.Bin` 下的 `$R*` 文件只带随机生成名，**原始文件名与路径存放于配对的 `$I*` 文件中**。因此：体量统计走 MFT；**面向用户的"这是什么文件"展示需解析 `$I*` 或调用 Shell API**（`Shell.Application.NameSpace(10)`）补全原始路径。回收站单独成项，并提供"清空回收站"的明确入口。

#### (6) Treemap 的共享字节归属（面积图不变式）

共享的硬链接字节会使"子项之和 == 父项"不成立。要求把已计入其它节点的共享字节归入显式的"**共享/余量桶**"，保证 Treemap 面积拼块**严格守恒**，避免图形与数字对不上。

#### (7) 其他特殊对象

- **稀疏 / 压缩文件**：按**分配大小**（`$DATA` 的 allocated，本机合计 **120.85 GB**）与**逻辑大小**（real size）分别统计，二者差异须可解释。
- **命名数据流**：本次 spike 只统计匿名 `$DATA`，因此遗漏 `$UsnJrnl:$J` 等命名流（可达数 GB）。M1 必须决定：**显式统计并归类**，或在**差额分解**中说明（见 §3.4）。
- **系统独占文件**：`pagefile.sys` / `swapfile.sys` / `hiberfil.sys` 单独标注"系统管理，不建议手工处理"。**注意一处早期错误**：早先以 `Test-Path` 判定这三者"均不存在"，而本次 MFT 实读发现 **`swapfile.sys` 实际存在且占 0.25 GB** —— 该结论已被推翻，也是改用 MFT 后**数据更真实**的一个例证。
- **云同步占位文件**（OneDrive 等"仅在线"）：需与实际占用区分，避免虚报。
- **NTFS 元数据文件**（`$MFT` 0.94 GB、`$LogFile`、`$Bitmap`、`$Secure` 等）：单独归类为"系统元数据"，**不进入"可清理"候选**。
### 3.4 差额分解 —— 必须能解释"对不上"

**实测**：磁盘已用 **145.13 GB**，MFT 文件大小合计仅 **117.92 GB**，**差额 27.21 GB 无法用文件大小解释**。已排除卷影副本（实测 **0 个还原点、0 个卷影副本**）。

已定位的可能去向：**NTFS 索引分配**（264,337 个目录的 `$INDEX_ALLOCATION`）、**命名数据流**（如 `$Extend\$UsnJrnl:$J`，USN 变更日志可达数 GB，本 spike 只统计匿名 `$DATA` 因而遗漏）、系统元数据（`$LogFile` 等）。该差额**尚未完全分解，列为 M1a 必须完成的验证项**。

**要求**：UI 与报告必须给出**差额分解**（文件 / 索引 / 元数据 / 命名流 / 未归属），**不允许"总计对不上已用空间"却沉默不解释**。

### 3.5 验证方法（M1 门禁）

- **三方对照**：C# MFT 结果 ↔ PowerShell `Get-ChildItem -Recurse` 求和 ↔ WizTree；差异 **< 2%** 且必须能解释。
- **回归基线**：附录 A.6 实测值（MFT 记录 989,696、物理 117.92 GB、逻辑 122.60 GB）。
- **专项用例**：DOS 别名过滤（185.26 → 122.60）、硬链接去重（757,385 → 724,225）、孤儿记录归属（45.59 GB 未归属须有解释或已消除）、差额分解。
- **提权路径**：分别在管理员 / 非管理员下验证行为符合预期。

## 4. 规则引擎（先于 AI 的核心）

**设计立场：能不能删，由本地规则表决定；AI 只负责把结论讲成人话。** 这样既省钱（绝大多数交互 0 token），又从根本上抑制幻觉。

### 4.1 规则表结构（`rules/*.json`）

```jsonc
{
  "id": "windows-winsxs",
  "matchers": {
    "pathPattern": "C:\\Windows\\WinSxS",   // 支持通配与变量：%LOCALAPPDATA%、%USERPROFILE%
    "matchType": "prefix",                    // prefix | glob | regex | exact
    "requireAdmin": false
  },
  "category": "system-component-store",
  "risk": "system",                           // safe | caution | risky | system
  "verdict": "do-not-delete",                 // keep | safe-to-clean | clean-with-care | do-not-delete | use-builtin-tool
  "what": "Windows 更新后保留的旧组件备份，用于随时回滚系统更新与修复损坏组件。",
  "why": "系统更新、修复与卸载功能依赖它。手动删除会导致后续更新失败、系统组件损坏且难以修复。",
  "advice": "不要手动删除。需要回收空间时使用系统自带的 DISM 组件清理命令。",
  "keepIf": ["近 30 天内安装过系统更新", "系统曾出现需要修复的问题"],
  "revert": "partial",                        // none | full | partial | via-builtin-tool
  "builtinTool": "DISM /Online /Cleanup-Image /StartComponentCleanup",
  "sizeSource": "physical",                   // 该规则的解释应基于哪种口径
  "tags": ["系统", "硬链接", "需管理员"]
}
```

### 4.2 匹配与决策流程

```
节点(路径/类型/大小) ──▶ 按优先级匹配规则（最长前缀 + 具体度排序）
        │
        ├─ 命中 ──▶ 输出 { category, risk, verdict, what, why, advice, revert }
        │             └─▶ 悬浮卡直接渲染（0 延迟 / 0 token）
        │
        └─ 未命中 ──▶ 通用启发式（按扩展名/路径特征/是否在用户文档域）
                      └─▶ 输出"未知项"结论：不判定为安全，风险默认 caution
```

**风险等级定义（不可被 AI 覆盖）**：

| 等级 | 含义 | UI 表现 |
|---|---|---|
| `safe` | 清理无副作用（如浏览器缓存、临时文件） | 绿色，可直接建议清理 |
| `caution` | 清理有代价但可接受（如需要重新下载/重新登录） | 黄色，说明代价后再建议 |
| `risky` | 可能影响功能或数据（如应用数据目录） | 橙色，默认不勾选 |
| `system` | 系统关键，禁止手动删除 | 红色，**禁止一键清理**，只给系统自带方案 |

**未知项默认 `caution`**：永远不把"我不认识"当作"它安全"。

### 4.3 规则库首批覆盖范围（按实测占用 + 可回收性排序）

**优先级依据（实测修正）**：全盘实测显示空间大头在**用户目录**而非系统目录 —— `C:\Users\<用户名>` **84.52 GB / 473,201 文件，占已用空间 58%**；`Windows` 29.69 GB、`Program Files` 11.74 GB、`ProgramData` 9.07 GB、`Program Files (x86)` 6.19 GB。因此**规则库必须先覆盖用户目录**，系统目录次之。

**同时必须诚实定位可回收量级**：实测真正"可安全清理"的总量**仅约 3 GB**（回收站 2.28 + Chrome/Edge 缓存 0.53 + Temp 0.16），而 WinSxS 的 9.99 GB **大部分不可回收**（硬链接与系统共享，DISM 仅能清理超期组件）。这决定了产品的价值主张是"**看清并解释**"，而非"清出大空间"（见 [PRD.md](PRD.md)）。

**首批规则覆盖**：

1. **用户目录优先**（占空间主体）：`AppData\Local`（含各类应用缓存）、`AppData\Local\Packages`（UWP 数据，实测 6.22 GB）、`AppData\Local\Temp`、`AppData\Roaming`、`Downloads`，以及文档/图片/视频目录（**只读展示，明确不建议清理**）。
2. **可安全清理项**（收益确定但量级有限）：回收站（需 Shell API）、`Windows\Temp`、`AppData\Local\Temp`、Chrome/Edge 缓存、着色器缓存、`Windows\Logs`。
3. **系统目录**（低收益 / 高风险，主要用于**解释与劝退**）：`WinSxS`、`Windows\Installer`、`SoftwareDistribution\Download`、`Prefetch`、`LiveKernelReports`、`ProgramData\Package Cache`，以及崩溃报告归档 `WER\ReportArchive`（实测**可清理但非管理员读不到**）。
4. **开发工具缓存**：npm / pip / uv / IDE 缓存等。

## 5. AI 网关

### 5.1 服务抽象（C#）

```csharp
public interface IExplainProvider
{
    string Id { get; }                       // openai | deepseek | anthropic | gemini | ollama | custom
    Task<ExplainResult> ExplainAsync(ExplainRequest request, CancellationToken ct);
    Task<ProbeResult> ProbeAsync(CancellationToken ct);                 // 设置页连通性自检
    Task<IReadOnlyList<ModelInfo>> ListModelsAsync(CancellationToken ct); // 自动发现可用模型
}
```

默认以 **OpenAI 兼容协议**为基准实现（`baseURL + apiKey + model` 三件套即可适配绝大多数服务与自建网关）；其余 provider 作为适配器实现。全部通过 `HttpClient`（`IHttpClientFactory`）发起，**不引入第三方 SDK**，以保持打包体积与依赖可控。
### 5.2 请求体设计（隐私红线）

**只发送结构化摘要，绝不发送文件内容、绝不发送完整路径中的用户隐私片段。**

```jsonc
{
  "nodeKind": "directory",
  "pathTemplate": "C:\\Windows\\<component-store>",   // 必要时对用户名等片段做脱敏
  "category": "system-component-store",
  "sizePhysicalGB": 9.99,
  "sizeLogicalGB": 14.3,
  "risk": "system",
  "matchedRuleId": "windows-winsxs",
  "fileCount": 84213,
  "userContext": { "windowsVersion": "10.0.19045" }
}
```

明确禁止项：文件名清单、文件内容、截图、用户目录下的具体文档名、任何可识别个人身份的信息。

### 5.3 输出契约与校验

模型必须返回结构化结果，本地做 schema 校验（失败则重试一次，再失败则降级）：

```jsonc
{
  "inPlainWords": "……",            // 这是什么（给完全不懂的人看）
  "relatedToUser": "……",           // 和用户自身内容/使用习惯的关联
  "impactIfDeleted": "……",         // 删了会发生什么（含具体症状）
  "canRevert": "partial",           // none | full | partial | via-builtin-tool
  "recommendation": "do-not-delete",// 允许的建议集合
  "expectedReclaimGB": 3.0,         // 必须 <= 本地计算的 physicalSize
  "confidence": "high"
}
```

**硬性护栏**：

1. `recommendation` **不得比本地规则的 `verdict` 更激进**（例如系统级项不允许模型改口为"可以删"）。越权则丢弃模型结果并回落本地文案。
2. `expectedReclaimGB` 不得超过本地算出的 `physicalSize`，超出即视为幻觉，钳制并标记。
3. 模型输出中的路径不得被当作可执行指令（不渲染为可点击的删除动作）。

### 5.4 缓存与降级

- **缓存键** = `matchedRuleId + category + 风险等级 + 取整后的大小档位 + provider/model`。同一类问题全盘只问一次。
- **降级链**：AI 可用 → AI 结果；AI 超时/失败/未配置 → 本地规则文案；两者都有 → 界面并排展示，标注来源。
- **计量**：记录每次调用 token 与耗时，设置页展示累计用量，让"花不花钱"对用户可见。
- **超时**：默认 20 s 上限；流式返回时首个 token 优先渲染。

### 5.5 密钥存储

- 存放于用户本地配置文件（`%APPDATA%\<app>\settings.json` 或系统凭据管理器），权限收紧到当前用户。
- **绝不写入日志**；日志中对 key 统一替换为 `sk-****`。
- **绝不进入导出报告**。
- 设置页支持"一键清除密钥"。

### 5.6 模型自动发现与测速（降低配置门槛）

"模型 ID"是小白用户填不出来的东西，这一步必须由工具承担。

**模型自动发现**

1. 用户只填两栏：`baseURL` + `apiKey`（provider 可自动识别）。
2. 服务端拉取模型列表：OpenAI 兼容协议为 `GET {baseURL}/models`；Ollama 为 `GET /api/tags`；Anthropic / Gemini 走各自适配器的列表方法。
3. 归一化为统一的 `ModelInfo[]` 交给前端下拉选择：

   ```ts
   interface ModelInfo {
     id: string;             // 真正传给 API 的模型 ID
     label: string;          // 展示名（可含上下文长度）
     providerId: string;
     contextWindow?: number;
     capabilities?: { vision?: boolean; jsonMode?: boolean };
   }
   ```

4. **必须保留手填兜底**：列表接口不存在、被网关禁用或返回非标准格式时，自动回退为手填输入框并说明原因。**不得因发现失败而阻断配置流程** —— 与"无 Key 也能用"是同一条原则。
5. 失败原因要区分并给出可操作提示：`401` Key 无效；`404` 地址不对（最常见的是漏写 `/v1`）；超时 → 地址不可达；非 JSON → 不是 OpenAI 兼容服务。
6. Key 只用于本次请求：不写日志、不回传前端；`GET /api/settings` 只返回"是否已配置"+ 掩码。

**模型测速**

目的不是跑分，而是让用户在候选模型之间**用数据做取舍**（"便宜但快" vs "贵但准"）。

- **测什么**：TTFT（首 token 时间）、总延迟、生成速度（`completion_tokens ÷ 生成耗时` = TPS）、以及**一次真实解释任务的结构化输出通过率**（能否通过 schema 校验）。
- **怎么测**：对用户勾选的候选模型并发发起（并发上限 3–5，避免触发限流），使用**固定的微型探针 prompt**（一小段磁盘条目的解释任务），受控 `max_tokens`（如 128），单模型超时 30 s、失败重试 1 次。
- **怎么展示**：三项原始数值 + 一个建议标签（"最快" / "最省" / "最准但不快"），**不合成单一分数排名** —— 输出质量无法用一个数概括，单一排名会误导选择。
- **成本透明**：测速会真实消耗 token，界面必须写明"本次测速预计消耗约 N tokens"，用户确认后再执行。
- **缓存**：同一 `baseURL + model` 的结果带时间戳缓存，7 天后可重测，避免每次打开设置页都花钱。

**为什么放在服务端而不是前端直连**：① 规避浏览器 CORS 限制（很多模型服务不允许浏览器直连）；② Key 不下发到前端，泄露面更小；③ 测速与用量可统一计量。

## 6. API 草案

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/scan` | 启动扫描；请求体含根路径、选项；**SSE 流式**返回进度（文件数、已扫体积、当前路径、未授权目录数）与最终结果 id |
| `GET` | `/api/tree?root=&depth=` | 取可视化用的聚合树（Treemap 数据源，按需分级下钻） |
| `GET` | `/api/node/:id` | 单节点详情：两种口径大小、分类、风险、命中规则、本地解释文案 |
| `POST` | `/api/explain` | 请求 AI 深入解释；命中缓存则直接返回；未配置 Key 返回明确的降级响应 |
| `POST` | `/api/explain/stream` | （可选）流式解释，改善体感 |
| `GET`/`PUT` | `/api/settings` | 读写 provider/baseURL/model 等；**`GET` 永不回传明文 key**（只回传是否已配置 + 掩码） |
| `POST` | `/api/settings/probe` | 连通性自检 |
| `POST` | `/api/settings/models` | 用给定 baseURL + key 拉取可用模型列表（自动发现）；失败时返回**可区分的错误原因**（401 / 404 / 超时 / 非 JSON），前端据此回退手填 |
| `POST` | `/api/settings/benchmark` | 对候选模型测速（TTFT / 总延迟 / TPS / 结构化输出通过率）；**执行前需前端确认 token 消耗**；可用 SSE 逐个回报进度 |
| `GET` | `/api/scan/:id/unreadable` | 未授权目录清单（对应 3.3-(2)） |

**约定**：所有接口仅绑定 `127.0.0.1`；写入类接口（M3 的清理）需带会话令牌，防本机其他程序误调。

## 7. 数据模型（SQLite 草案）

```sql
nodes(id, parent_id, name, path, kind, file_id, logical_size, allocated_size,
      physical_size, name_entry_count, shared_bytes,
      file_count, dir_count, risk, category, is_orphan);

rules_applied(node_id, rule_id, verdict, risk, matched_at);

explanations(cache_key PRIMARY KEY, rule_id, category, risk, size_bucket,
             provider, model, payload_json, created_at, tokens_in, tokens_out);

scan_runs(id, root, started_at, finished_at, cancelled, scanner_kind,
          record_count, file_count, dir_count,
          physical_bytes, logical_bytes, allocated_bytes,
          reparse_count, orphan_count);

unowned_nodes(scan_run_id, reason, sample_path, node_count, bytes);
size_reconciliation(scan_run_id, bucket, bytes, note);

settings(key, value_enc, updated_at);
```

> **变更说明**：`unreadable_paths` 在 MFT 路线下不再必要（MFT 绕过 ACL，见 §3.3(4)），替换为 **`unowned_nodes`（孤儿/未归属桶）** 与 **`size_reconciliation`（差额分解）** —— 直接对应实测发现的 **11,455 条孤儿记录**与 **27.21 GB 未解释差额**。

索引要点：`nodes(parent_id)`、`nodes(path)`、`nodes(file_id)`（硬链接去重与物理占用汇总）、`explanations(cache_key)`。百万级节点的写入建议**批量事务提交**，避免逐行 fsync。

## 8. 安全模型

| 层 | 措施 |
|---|---|
| 扫描阶段 | 全程只读；不跟随 junction/symlink；不写任何被扫描目录 |
| 权限（**新增风险**） | 应用以**管理员**运行（MFT 必需），意味着**任何缺陷的影响面都被放大**。要求：① 除读取 `$MFT` 与用户显式确认的清理外，不进行任何特权操作；② 不访问网络、不修改系统设置；③ 代码审查重点覆盖路径拼接与删除边界 |
| 展示阶段 | 风控等级由本地规则决定；`system` 级永不可被标记为可清理 |
| AI 阶段 | 只发统计摘要；输出做 schema 校验 + 越权钳制；不把模型输出当可执行指令 |
| 清理阶段（M3） | 删前精确清单 → 二次确认 → **仅删除到回收站** → 结果留痕报告；高危路径额外确认，不可绕过；白名单保护 |
| 本地服务 | 仅回环监听；写操作需令牌；CORS 收紧 |
| 隐私 | Key 不记日志、不进报告；提供"完全离线模式"（禁用全部外发，仅用本地规则） |

**清理能力（M3 起）只提供"删除到回收站"**：不提供永久删除，也不提供任何"一键清理全部"的入口。


| `C:\$Recycle.Bin\S-1-5-18` | **EPERM**，回收站 2.28 GB **完全不可见** | **可见**（`$R*` 记录含大小；原始名需解析 `$I*` 或 Shell API） |
| `C:\Program Files\WindowsApps` | 求和 **0.00 GB**（读不到） | **可见** |
| `...\WER\ReportArchive\AppCrash_*` | EPERM（大量） | **可见** |
| **删除能力** | 受 ACL 限制 | **同样受 ACL 限制** —— 看得见 ≠ 删得掉 |

**结论**：MFT 使**分析完整度问题基本解决**（不再需要"结果为下界"的常驻告警）；但**删除权限不受影响**，故"可清理"判定必须区分"看得见"与"删得掉"（见 §3.3(4)）。

| 结论 | 依据 |
|---|---|
