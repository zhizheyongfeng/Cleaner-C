# MFT 直读原型（spike）· 一次性验证代码

> ⚠️ **这是探索性原型，不是产品代码。** 它的唯一目的是回答一个问题：**MFT 直读到底能不能做到秒级，以及有哪些坑。**
> M1a 会在 `CleanerC.Scan` 中**重写**它（更完整的错误处理、流式 API、测试覆盖）。请不要在这里叠加功能。

## 它验证了什么

| 结论 | 实测（本机 C 盘，2026-09-17） |
|---|---|
| 可行且极快 | **2.19 s** 处理 **989,696** 条 MFT 记录（纯解析 1.80 s），解析错误 0 |
| 相对目录遍历的加速 | 约 **40 倍**（目录遍历 87.8 s） |
| 必须提权 | 非管理员 `CreateFile('\\.\C:')` → `Win32Error=5` |
| 必须过滤 DOS 8.3 别名 | 642,368 条别名（39%）→ 不过滤会虚高 **51%** |
| 必须去重硬链接 | 物理文件 724,225 vs 目录项 757,385 |
| 必须处理孤儿记录 | 11,455 条父指针为 0 → 45.59 GB 归属失败 |
| 必须扇区对齐读取 | 非对齐 → `ReadFile err=87` |
| 引导扇区 `0x40`/`0x44` 是有符号单字节 | `0xF6` = −10 → 1024（误读为 246 会全线失败） |

完整说明见 [`docs/ARCHITECTURE.md`](../../docs/ARCHITECTURE.md) §3 与附录 A.8/A.9；原始输出见 [`docs/measurements/mft-report-2026-09-17.txt`](../../docs/measurements/mft-report-2026-09-17.txt)。

## 运行方式（需要管理员权限）

```bash
dotnet build -c Release
# 以管理员身份运行，参数为报告输出路径
./bin/Release/net10.0/mft-reader.exe ./mft-report.txt
```

提权运行（Windows）：

```powershell
Start-Process -FilePath .\bin\Release\net10.0\mft-reader.exe `
  -ArgumentList '"' + (Join-Path $PWD 'mft-report.txt') + '"' -Verb RunAs -Wait
```

## 已知缺陷（M1a 需修，不在本原型范围内）

1. **45.59 GB 归属失败**：孤儿记录（父指针为 0）未做三级回退。
2. **命名数据流未统计**：只统计匿名 `$DATA`，遗漏 `$Extend\$UsnJrnl:$J` 等。
3. **索引分配未统计**：264,337 个目录的 `$INDEX_ALLOCATION` 未计入，导致差额分解不完整（145.13 − 117.92 = 27.21 GB 待解释）。
4. 单卷硬编码（`\\.\C:`）、无流式 API、无单元测试。

5. **个别目录名解码为乱码**：原始报告中可看到一条乱码顶层目录名（`Progr籽쫻…AV0000`，体量 0.00 GB）。原因是 `$FILE_NAME` 名称段的边界处理在少数记录上不正确（可能涉及跨扇区或短名条目）。**这是解析边界缺陷，M1a 必须覆盖**；当前不影响总量口径（该条目体量近似 0）。
6. **报告为原始输出**：报告的「顶层目录」一栏按 MFT 记录的**主父目录**归属，孤儿记录（缺陷 1）会落入「未归属」桶；该数字本身即为结论之一，不是 bug 的隐藏。
